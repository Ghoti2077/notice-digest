# notice-digest

把**学校/班级群的通知**自动筛出来、写成大白话、推到飞书，顺手记进多维表格当任务台账。

不是「把每条消息都转发给你」——群里的水话、表情、接话全部丢掉，只留**真的要你办的事**。

```
网页列表(VSB站群) ┐
                  ├─> 模型筛+摘要 ─> 飞书卡片（重点置顶/过期折叠）
微信群消息        ┘                 ├─> 飞书待办（带截止提醒）
                                   └─> 多维表格台账（自动标过期、清旧行）
```

## 它解决什么

- 公告站一天发十几条，八条跟你无关，两条要你办事 —— 只推那两条
- 群里 @所有人 的通知被 200 条闲聊淹掉 —— 现在单独摘出来
- 「截止10月29日」这种，过期了你还当新的看 —— 程序算日期，过期自动沉底并标「已过期 N 天」
- 看完就忘 —— 3 天内要办的自动变成飞书待办，飞书自己提醒你

## 快速开始

```bash
pip install requests   # 只有微信群源需要额外依赖，见下
cp config.example.py config.py
# 编辑 config.py：填飞书应用凭证、模型 key、你要盯的站点/群
python push.py --dry-run       # 网页源，只打印不推送
python push.py                 # 真推
```

微信群源额外需要 [`wechatauto-replica`](https://github.com/fanyuantaier/wechatauto-replica)（读微信 4.x 本地库，解密后轮询增量）：

```bash
pip install wechatauto-replica
python wechat.py --self-test   # 不联网，验日期分档
python wechat.py --dry-run
```

两个脚本都可以挂 cron：`0 8 * * *` / `10 8 * * *`（错开几分钟别挤一起）。

## 飞书应用要开的权限

自建应用（open.feishu.cn）里逐项开，**每次改完必须去「版本管理与发布」发新版本**，不发版不生效：

| 权限 | 用来干什么 | 不开会怎样 |
|---|---|---|
| `im:message` | 发消息 | 什么都发不出去 |
| `task:task:write` | 建飞书待办 | 只发卡片，不建待办 |
| `bitable:app` | 读写多维表格 | 不写台账 |

⚠️ 多维表格还要**单独**把这应用加成那张表的「可编辑」协作者（右上角 ··· → 协作者）。开放平台权限只代表「这个应用能调接口」，不代表「它能看你那张表」，两层都要过。

## 配置说明

`config.py` 里三块：

- `WEB`：公告站列表页 URL、栏目 id→名字映射、哪些栏目写详细摘要。栏目 id 从文章 URL 能认出来：`info/<栏目id>/<文章id>.htm`
- `WECHAT`：群名 + 微信数据目录名（`wxid_xxx_0000`，用 `wechatauto.list_accounts()` 查）
- `BITABLE`：`app` 留空就不写台账

模型链默认 `glm-4.6 → glm-4-flash → 火山方舟`，前一个挂了自动降级，在 `LLM` 里改。

## 几个踩过的坑（改代码前先读）

**日期一律程序算，不让模型算。**
实测让 LLM 判断「这条过期了吗」，它会把 10月20日截止的标成「3 天内紧急」。现在模型只判断「这段话是不是通知、说的是什么」，日期用正则 + `datetime` 算死。

**相对时间以消息发出日为基准。**
群里 10月29日 有人发「明天下午两点半开会」，拿今天的明天去算会永远显示「还有 1 天」。基准必须是那条消息的 `create_time`。

**绝对日期优先于「明天/今晚」。**
文本里同时出现「10月29日」和「明天」时用前者。

**分三档，不是两档。**
`high`（3 天内截止，置顶加粗）／`normal`／`expired`（已过期，收进折叠面板）。只有两档时，补推历史会把过期通知当新通知推给用户。

**飞书卡片用 JSON 2.0。**
`{"schema":"2.0","header":{...},"body":{"elements":[...]}}`，正文组件 `{"tag":"markdown","content":"..."}`。写成 1.0 的顶层 `elements` 会静默不显示，不报错。

**相邻 markdown 元素会挤在一起。**
条目之间插 `{"tag":"hr"}` 才有呼吸感。

**正文别整句加粗。**
粗体只给分区标题（`⚡ 3 天内要办`），条目用 `▎还有 1 天 · 发送者` 做锚点，层次靠「分区 > 锚点 > 全角空格缩进」三层，不靠字重。

**模型会偷懒。**
偶尔不给必填字段、`what` 只丢一个标题式短句。`pick()` 里有质量闸门：劣质条目超过 1/3 就自动重跑一次。

**去重用源自己的稳定 id。**
文章 id / 群消息 `local_id`，别用时间戳（同秒多条、时区、补推全乱）。

**首次跑会建基线。**
只记游标不推送，否则用户先吃一屏旧通知。反过来说：用户说「这几条我没收到」时，先查是不是被基线吞了。

## 自检

两个脚本都带 `--self-test`：不联网、不读外部服务，只验解析/日期分档/渲染分支。日期逻辑每改一次都应该有回归用例 —— 这类 bug 不报错、不崩溃，只是静默算错，用户比你先发现。
